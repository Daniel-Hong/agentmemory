# SDK completion return (development candidate)

The user chose the stock SDK acknowledgement boundary after the file-backed engine review found no public per-record disk-commit receipt API. This deliberately removes the fork's additional namespace-file readback/fsync from ordinary SDK completion, not from the retained explicit disk-proof implementation. No sudden-power-loss durability guarantee is claimed for SDK state.

StateKV uses completion:sdk/completed:true/synced:false. Sticky SDK mutation errors, freeze/drain, bounded captures, pinned expected-value checks and original deadlines remain. Shutdown receipts distinguish completed from verified; SDK-only shutdown must not produce a clean disk-writer proof. No historical failure, uncertain outcome, recovery budget or circuit is reset. No storage schema migration or engine update is included.

## Capture ownership

Only a caller sending captureCompletion:sdk-v1 receives SDK completion acknowledgement, and only after completed SDK capture or a matching existing observation. An SDK-tagged inbox whose observation is missing receives a hold, not a completion receipt. No boot/time-based durability mark is issued in SDK mode. Old clients continue to receive a conservative 503 and preserve their original under their existing delivery policy; server-only deployment cannot normalize those clients.

Updated ordinary clients (shared createCapture, DSH and stock hook capture) first fsync a private local original, then send. These originals are separate from retry rows and are never aged out, reconciled away or evicted. Existing record-size and total spool limits apply; original retention consumes the total quota. Admission fails before sending when retention cannot be secured. The archive denotes retained source, not proof of server completion. If a stable event is delivered with a changed timestamp or prompt backfill annotation but the same source/identity, a separate immutable envelope is retained before the current body is sent. Real source/identity conflicts remain blocked. Event-ID-only restoration is held when multiple envelopes make source selection ambiguous; no envelope is silently chosen or deleted. Temporary writes use fsync/rename/directory sync; abandoned crash temporaries consume quota. Windows directory sync has the pre-existing platform limitation.

Updated Codex compatibility hooks mark only new observation outbox rows with completionPolicy:sdk-v1; old bodies/policies are not rewritten. After explicit SDK completion, the existing fsynced source record is moved to accepted-originals and both directory entries are synced. New capture admission counts pending, held, corrupt and accepted originals against AGENTMEMORY_CAPTURE_SPOOL_MAX_BYTES (default 5 MiB). No originals are automatically deleted at capacity; new enqueue reports capture_originals_full. This bounds storage but requires a later explicit source retention/export policy for long-running operation. Session start/end rows keep their prior contract.

SDK_COMPLETION_ONLY is a permanent hold for updated senders: shared spool rows retain their body/attempt count with holdReason, and compatibility outbox rows retain the complete file with .held suffix. They are not periodically resent and do not block later compatible records. SDK/legacy identity is not deduplicated across policy boundaries; receipt-required rows cannot be dropped merely because a same-ID SDK row succeeded. Old unupdated senders may still retry 503; updating the participating clients is part of any usable rollout.

New client/old server retains its local originals. The initial HTTP response is reused by legacy handoff rather than issuing a second POST. Old-server normal acknowledgement uses the previous mark/receipt contract; missing required proof never becomes success. Unknown/incomplete SDK responses remain unacknowledged. The original retained server inbox remains separate from active retry counts, with its own bounded capacity. This is SDK acceptance plus source preservation, not disk-proven receipt delivery.

## Held operations

Existing quarantine/recovery/manual retry jobs, managed receipt-required spool settlement, legacy vector/BM25 migration/deletion and audit migration/retention stay held in SDK mode. Original dead-letter records, histories and budgets are preserved. Ordinary summary/compression/embedding and current-format index writes use SDK completion, subject to existing admission/holds and normal SDK failures. Queries/rebuilds may still read data. This candidate cannot be described as full quarantine recovery or absence of all read/LLM costs.

## Validation and rollout boundary

RED/GREEN tests cover acknowledgement opt-in, archival before POST, restart via serialized test state, duplicate suppression, missing observations, mixed policy queues, capacity/expiry, conflict preservation and injected file-write/fsync/rename/directory-sync failures. End-to-end tests wire the actual API/capture/observe/client modules to a synthetic KV transport; worker-controller recreation is not an actual engine process restart or power-loss test. No production data, port, service or installed hook is used.

The initially blocked full suite was explicitly authorized and executed with a temporary HOME and one fork worker. Its first result was 5,227 passed, 87 failed and 13 skipped. After fixture contract repairs and concrete product regression fixes, the final full suite passed **5,332 tests, with 13 pre-existing conditional tests skipped and no failures**. Build, skills generation/check and docs sync/check also passed. No assertions, product deadlines or safety criteria were weakened to pass the suite. The installed SDK0.25/engine0.22.1 small isolated source-restoration test passed normal full engine/worker restart: three canonical observations and three retained inbox sources survived, with local originals and legacy/budget history unchanged. Native publication windows were observed, not promoted to per-record fsync proof. Full worker scheduling, sudden power loss and the operating engine's active publication cadence remain unverified. A strict disk experimental fixture had an earlier intermittent index-publication readback failure that could not be causally resolved; the final full run passed it with its strict assertions retained. This is not proof that the discarded disk certification architecture is fixed.

The candidate also includes the previously integrated official 0.9.31/SDK0.25 work and approved receipt normalization/late-join work; it is not a one-line server hotfix. No engine binary is updated. A rollout proposal must name the server package and matching generated client/hook files, preserve existing originals/accepted-originals/held files and the 114 quarantine plus legacy record, keep automatic recovery OFF, and validate ordinary new captures before general resume. Deployment/restart/client installation are not performed here. Existing strict external release/rollback guards must be reviewed for completed-versus-verified compatibility; no flag may be forced true.

Upstream replacement criterion: stock SDK acknowledgement can replace this ordinary path once mixed-version source ownership/preservation and truthful completion metadata are equivalent. Optional future disk proof requires an independently supported contract, not a relabelled SDK response.

## Selected SDK source restoration

The development candidate adds authenticated `POST /agentmemory/capture/restore-sdk` for exactly one selected SDK-policy original. Existing secret/authentication is reused; no new credentials, global automatic replay, quarantine retry or background activation is introduced. The endpoint requires a valid client event ID, timestamp, identity and explicit sdk-v1 policy. Text payloads are limited to 256 KiB; image/unknown/mismatched sources stay held.

The installed engine0.22.1 function metadata exposes get/set/update/delete/list/list_groups, not a public CAS. Restoration therefore requires the **existing native file-writer lease, verified cold engine/worker boundary and per-record exclusive StateKV mutation gate**. It is unavailable without those conditions or while normal holds apply. This is conditional creation among supported single-writer application paths; it is not an engine-wide CAS against arbitrary direct state clients. It never relaxes the prior writer/hold guards.

The source is checked before admission, again immediately before missing-canonical creation inside observe's record gate, and once more before SDK ACK. New history, receipt/tombstone, dead status, source change or writer uncertainty blocks completion. An existing matching observation is not overwritten; conflicting same-ID content remains held. New inbox originals share ordinary capture admission/quota. Restore metadata is either wholly absent or a complete valid request UUID/state/0..3 counter; partial/malformed metadata is not repaired by overwriting it. Up to three explicit missing-source restore attempts are allowed, with no old attempts/circuit/history reset. No attempt runs automatically.

`restoreObservationOriginal(eventId)` in the stock capture helper selects one immutable shared SDK original. `HookClient.restoreOriginal(name)` selects one file from Codex `accepted-originals`. Both retain the source byte-for-byte on success, rejection, unsupported old server and uncertain transport. They use only the dedicated restore endpoint; there is no ordinary-send fallback. These are API/client methods, not a new Viewer picker or global scheduler. They do not select legacy/receipt-required originals.

A source restore uses ordinary observation construction/index preparation while creating only an absent canonical value under the verified writer gate. Pre-existing session lifecycle, endedAt, updatedAt and summary cursor are preserved; the current count is derived from the existing observation snapshot rather than incrementing an already-surviving count again. An observation that wins the conditional-create race is treated as duplicate. A body-free audit records `verify_pending`; only final SDK source/inbox validation produces completion. Existing matching canonical data is never rewritten, and this does not claim reconstruction of every missing derived session/summary/graph record or historical outcome.

The operation joins existing capture drain tracking. Shutdown/hold/error during restoration retains a pending original and does not ACK completion; explicit recheck can classify the surviving observation on the next supported writer boundary. Pending source verification is shown separately in the inbox UI. SDK completion still has no per-record fsync proof. Existing native CLI publication window remains part of normal shutdown, and sudden stop/power loss before publication remains a stock-contract limit.

## Native compatibility and release preparation follow-up

The verified 4fd5566 source remains immutable in its original checkout. The separate follow-up adds `--native-compat`, requiring explicit absolute `AGENTMEMORY_NATIVE_III_BIN` and `AGENTMEMORY_III_CONFIG` paths and exact installed engine0.22.1. Without the selector the official Compose path is unchanged. Native mode never installs, downloads or falls back to another engine. It renders a separate runtime configuration using the selected data/loopback ports and preserves the seed's publication interval. A republished runtime file with an empty worker list cannot shorten that cached interval.

Engine and worker shutdown require matching process start/executable/arguments evidence before any signal; stale or missing worker identity fails closed. Normal SIGTERM and publication wait remain. The native selector is used by both start and stop in the development service drop-in. It does not authorize service or host operation.

The server build bundles SDK0.25, helpers0.25, YAML2.8.1 and JSON52.2.3 plus their imported closure. A generated hash-bound JavaScript inventory records remaining literal external imports. The development release kit independently checks the complete packed inventory and narrowly permits only these four dependency changes while preserving the old dependency-tree link for unchanged packages. The proof is a reviewed build artifact, not a general sandbox for arbitrary JavaScript. No npm installation or dependency overlay is required on the operating host.

SDK shutdown acceptance is opt-in to the reviewed candidate, requires a fresh matching worker receipt with both completion flags, zero mutation failures and observed exit of all expected processes, and never changes verified/synced to true. The initial stop of the old .32 release still uses its strict disk guard. After SDK candidate startup, a code-only .32 downgrade preserves all SDK source/state files and leaves the service fully stopped with manual compatibility review required. It cannot automatically restart an old writer over new SDK inbox state. Source preservation includes the shared XDG capture spool as well as client legacy/accepted/held rows, using a pinned, same-user staging copy without changing privileged directory permissions. The development kit has not been installed or registered. The existing explicit reviewed-kit bootstrap used by the SSH enrollment scripts already preserves SDK metadata and the exact three-file client transition; it does not require extending the separate delegated candidate-enrollment API or its global policy. A proposed delegated-policy expansion was preserved outside the candidate and reverted. Synthetic preparation/bootstrap/catalog/static-proof tests cover the existing route, with no service invocation or installed-policy change.

The follow-up also repairs bare-environment hook subprocesses: a real temporary HOME plus explicit config/data/spool paths is checked by a child metadata probe before capture. Two previously written real-home SDK archives were internally matched to the known synthetic fixture without exposing record identifiers or digests. They were not deleted or modified. Earlier test-pass evidence did not prove complete home isolation; subsequent focused/full follow-up results must be reported separately.

## Remaining operating gates

The server package and matching three active Codex compatibility files (`_capture.mjs`, `long-session-hook-client.mjs`, `manifest.json`) must be applied together under a specific operating approval. Existing wrapper paths can remain unchanged. Other client installations are not silently updated. The default5MiB retained-source quota has no automatic deletion; currently measured eligible metadata fits, but continuing collection eventually needs an explicit retention/export decision. Existing legacy1, quarantine114, capture budgets/circuit/history and automatic recovery OFF must survive installation.

Operating native startup, reviewed candidate-kit enrollment and package/client installation remain unperformed. The installed global enrollment bootstrap, authorization and policy remain unchanged; each new candidate still requires the normal explicit review of its frozen kit bytes. New SDK completion does not resolve old historical uncertain mutations or prove power-loss durability. Initial old-release strict-disk verification can still block deployment; no guard may be bypassed. Post-install validation must distinguish ordinary new capture/processing from intentionally held old proof-required recovery. No push, enrollment, deployment, installed hook change, service restart, hold release or operating replay was performed in this follow-up.
