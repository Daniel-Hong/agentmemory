# Two-file Ubuntu client transition — preparation only

The .15 server still uses the retained .3 Ubuntu Codex capture client. Nine hook commands and thirteen retained compatibility files are protected. This change adds no new privileged endpoint, daemon, sudo rule, arbitrary path, shell program or remote installation. Default kits continue to reject every compatibility change.

An explicitly administrator-reviewed kit may contain `clientTransition:{version:1,files:{...}}` with exactly `plugin/scripts/codex-compat/_capture.mjs` and `plugin/scripts/codex-compat/manifest.json`. Each entry must bind `before` to both the baseline compatibility table and protected retained file, and `after` to the reviewed package. The other eleven files must match. The retained root is restricted to the existing Ubuntu personal client release directory; hooks.json, the nine hook commands, credentials, Windows and permission configuration stay unchanged.

The transaction still requires current guard, reviewed package/dependencies, storage-certified stop, fresh private backup, preserved archives, file/directory fsync, readback, runtime/data verification and a real activation receipt. Client copying runs as the existing service user. Old rollback bytes are read in that user phase from one O_NOFOLLOW regular-file descriptor with a 1MiB ceiling and exact before-hash verification; root never opens these client bytes. Copies are atomic; a partial failure restores only known before/after client files and old server code, with latest data/queues/holds/recovery budgets retained. Unrecognized bytes, busy clients, failed storage certification or incomplete recovery leave conservative inspection state. Prior immutable preservation archives are never overwritten.

## Actual exclusion boundary

The user phase participates in the existing client's Lamport `.worker.lock.tickets` then `.flush.lock.tickets`, with the same choosing/ticket/token ordering and short bounded refusal. An existing worker holding its ticket blocks transition; a foreground flush cannot import the handoff module while the flush ticket is held. Only this transaction's UUID lock files are removed. Existing queue records and other owners' tickets are not deleted. Synthetic tests run the real existing Node client against these locks and verify zero network requests and original ownership retained.

This excludes legacy handoff and worker import, not every possible capture module user. The existing managed drain child can import outside these two locks. Its `_capture.mjs` is a standalone bundle with builtin imports only, replaced atomically, so it gets one complete old/new module; manifest.json is not executed or read by capture code. Generated .3/new bundle comparisons confirm runDrainChild, appendSpool, retainSent, reconcileSent and drainSpool unchanged. Do not claim all already running clients adopted the new module or that source hashes certify live ingestion. The process scan is a supplementary refusal check, not the synchronization proof. Unrecognized custom outbox directories/launchers are outside this targeted Ubuntu deployment and require separate inventory.

## Recovery pair

Prepare primary .16 and compatible recovery .17 from the same reviewed source. Recovery .17 preserves the receipt fix and new two-file client pair, but has the existing tested v2/automaticMemoryRecovery:false build profile. Both kits bind the identical real .15 baseline and identical transition. After a .16 start failure, the existing stopped-recovery procedure verifies failed code, certified shutdown, latest data and holds/budget before admitting .17. It accepts already transitioned files only when the verified stopped-recovery plan binds their exact after hashes. The duplicate completed recovery verifies real state and does not restart again. Partial/unrecognized states require manual inspection; no forced process kill or data rewind is added.

This recovery package is deliberately new; the old .12-from14 kit cannot certify the new pair. Direct .11 downgrade remains prohibited. A future .15 code rollback, if desired, must also restore the exact archived old two client files under reviewed guards; replacing only server files is not a completed client rollback.

## Operational boundary and outstanding limits

Development and synthetic tests only. Actual root review/enrollment, activation, service or client restart, retry/retransmission/deletion, permission changes and Windows access are not authorized by this preparation. Administrator SSH review must cover the changed runtime and both fixed artifact hashes before registration; review-template approval remains false. Registration alone does not apply or restart anything.

Server startup already drains managed spool and capture inbox; this existing side effect is part of later restart approval. Legacy outbox retries are separate and can start on future hooks. Operational activation must explicitly distinguish these automatic existing paths and any approved bounded legacy processing. Large unsupported source shapes can still exceed the existing 15MiB transport budget. Preserve and hold such originals; this patch does not implement lossless fragmentation or establish loss/recovery for historical attempts. No timeout, provider serialization/input budget, external notification, web enrollment or Investment change is included. Windows Daniel_Desktop is connected but not attached/authorized for this task; its installation remains unverified and no access is attempted.

Upstream replacement requires exact two-file authorization, unsupported-path rejection, no privileged read/write race, real client lock compatibility, partial rollback, same-baseline stopped recovery and duplicate recovery tests. Long-term memory recording remains separately reviewed.
