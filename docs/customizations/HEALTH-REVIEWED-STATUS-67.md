# Health current-state display for existing recovery history

The Health cleanup uses the existing SDK reconciliation and summary coverage evidence. Capture recovery checkpoints retain their original phases and attempt history. A checkpoint whose key, event, session, observation and source digest match an existing committed SDK resolution is counted separately as sdkReviewed. Disk-resolved totals retain their existing meaning. Unmatched, incomplete and unavailable records continue to contribute to the warning. The recovery dialog reports the existing SDK completion count.

The sessions endpoint supports opt-in summary coverage metadata for Health. When summaryProgress is absent, it reads a bounded small-session source set and uses the existing summaryCovers fingerprint. Source changes, missing records, read failures and timeouts leave coverage unknown. A confirmed count is returned as response metadata. The viewer uses that count in its remaining-work and throughput views. Scheduling and persisted session records use their existing fields.

The regression checks cover matching SDK history with unchanged storage, mismatched digest and incomplete SDK resolution, source and fingerprint changes, existing-progress precedence, and the opt-in API contract. Operation uses the normal .67 deployment procedure with version-matched boot and manual recovery helpers. Live acceptance requires the former warning to disappear, sdkReviewed to reflect the two recorded resolutions, and the Windows validation summary to appear current with zero remaining work. The original recovery rows and summaryProgress absence are rechecked after deployment.
