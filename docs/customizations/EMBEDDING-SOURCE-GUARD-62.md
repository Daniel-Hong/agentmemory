# Selected-source embedding certification: .62 server preparation

An SDK capture stores its observation and embedding intent under the session lock, then releases that lock before waiting for certification. The .60/.61 deferred source check remembered the mutation revision for the entire observation namespace. A second, unrelated observation in the same session changed that revision and caused `EMBEDDING_SOURCE_CHANGED`, even though the selected observation and intent remained intact. A synthetic regression reproduced this rejection before any product edit.

The source check now acquires a selected-key watch from the existing state durability fence. It reuses the fence's revision observers, which are notified both before and after every mutation and remain valid across dirty-key pruning. A WeakMap associates only active mutation promises with their key, so registration also rejects a target mutation that was already in progress. It introduces no permanent per-record revision history. The watch is released on successful/failed certification, prepare failure and worker stop. New capture acquires its certifier immediately before returning from the session lock, after viewer/logging side effects, so an earlier viewer exception cannot leak an unstarted watch. Raw observation/inbox preservation and same-observation retry are regression-tested. Viewer events already precede final certification and are not SDK ACKs; the HTTP result still awaits the complete certificate. A missing selected-key facility refuses deferred file certification; callers without that facility retain the existing synchronous fenced path.

Another key may be written while the selected source is certified. Source replacement, deletion/recreation and ABA still invalidate its watch, including SDK writes that apply before returning a lost response. Source row identity, intent generation and the original source-plus-intent fence remain required. An uncertain unrelated SDK mutation still causes the existing fence refusal; this change does not reinterpret SDK acknowledgement as disk durability. The namespace-wide guards remain in observation readers and receipt inspection where full-namespace consistency is required.

Scope: based on .61 source commit `f8246e56eb666ef0f9cefa9135ccbe4df5b9deb6`; the new server behavior is limited to `observe.ts`, `embedding-recovery.mjs`, `state-durability.mjs` and its declaration. Relative to the running .60 server, the source also inherits the already prepared .61 client spool/delivery repair and generated version metadata. No batch size, pump ordering, publication evidence retention, provider behavior, actual source/ref data or recovery authorization changes are included. The installed .61 client and .60 server are not modified by this preparation.

Coverage includes unchanged selected sources with another same-session SDK write pending before/after preparation, real target ABA, applied-but-lost responses, missing guards/fences, intent replacement, pruning, source preservation and watch lifecycle cleanup. Uncertain SDK replies preserve the existing `STATE_DURABILITY_TIMEOUT`/`SDK_MUTATION_UNCERTAIN` diagnostic shape. All tests use synthetic state, a real temporary HOME and a single default fork worker.
