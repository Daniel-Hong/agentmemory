# Verified capture quarantine reconciliation

Development only; operating .27, its storage-error hold and outstanding manual recovery remain unchanged. Default OFF (`AGENTMEMORY_AUTO_CAPTURE_RECOVERY=true` is an explicit later activation decision). No new endpoint, credentials, external notifications or LLM calls.

The existing retry scheduler reruns incomplete capture work within its own budget. This separate coordinator reconciles only quarantined transient failures whose original observation and current keyword/vector publication already exist. It never calls observe/compress/embedding, resets capture attempts, clears historical counts or recreates missing originals. Missing/conflicting/unknown content, active/manual retry, deletion markers and unready indexes stay blocked with a reason. Initial synthetic and compressed observation publications are supported; memory publications are rejected.

Every minute, at most one eligible item is considered after a 60-second cooldown, under existing manual/deployment/memory background admission. A durable checkpoint precedes completion changes. Six records (history, inbox, canonical original, intent, committed marker and receipt) are fully disk-certified against expected values, checked again under their record gates, then completion history/receipt and normal inbox removal are reconciled. Long full-file certification stays outside the gates. Unrelated record writes continue. A second complete certification and fresh-value check are required before resolved state is reported. A failed final proof leaves verification pending, not delivered success; subsequent work verifies without replaying capture. Three proof failures exhaust the item budget; repeated failures open a 30-minute circuit. No automatic reset of exhausted/blocked items.

Writer safety is limited to one compatible Linux worker, local engine and local file store on the same host. A parent-held flock FD excludes another participating worker. All StateKV mutations pass the selected-record gates; SDK write rejection latches automatic changes off because it does not cancel engine work. Redis, nonparticipating/direct writers, shared/network stores, copied/migrated lock metadata and forwarded engine connections are unsupported. Lock ownership is not proof of cancellation.

A retained lock marker binds dirty/clean status to Linux boot identity. First installation and same-boot unclean restarts cannot claim a safe writer epoch; they remain held (`WRITER_EPOCH_UNVERIFIED`). An ordinary clean worker cycle cannot clear this uncertainty. A later same-host OS boot boundary with a local engine proves prior local processes ended. Thereafter only existing verified shutdown plus settled StateKV mutations, no mutation errors, successful SDK disconnect and valid prior admission may preserve clean status. No new reboot/reset command is introduced. Activation planning must account for this conservative first-use requirement; the unresolved NVMe incident makes an operating reboot/activation inappropriate to infer here.

Existing status API exposes only aggregate enabled/supported/phase, resolved/verifying/blocked counts, whitelisted reason counts and circuit timing. HTML/Viewer keep unverified completion visible even when its normal inbox copy was removed. Private checkpoint identifiers/digests remain in the normal local state store and are never returned by this status. Historical 190 spool attempts have no individual identities and remain unknown history; this feature cannot retroactively prove their delivery.

Costs: one small lock marker fsync at startup/verified shutdown; selected checkpoint writes and the existing full durable fences per eligible item. The SDK history/recovery list is still unpaged (hard accepted-row limits 5000/5001 do not bound transport allocation). No performance gain or hard SDK-memory bound is claimed. Unsupported or failed metadata reads halt the coordinator. No pruning of recovery evidence is implemented; reaching the cap requires inspection.

Validation uses synthetic fixtures, one Vitest fork and temporary HOME. No real engine, production originals, new LLM work, full browser suite or large benchmark runs in this phase. Full aggregate suite/release gate and representative live activation remain unverified due the user-requested low-load constraint after NVMe I/O errors. A code rollback must stop the newer worker before older code starts and retain checkpoint/lock/original/history state; older code will not interpret automatic recovery status. There is no data rollback.

Upstream replacement criteria: equivalent source/identity checks, atomic writer coordination, ACK-after-fsync proofs, interrupted verification resumption, explicit unknown outcomes, and the same conflict/deletion/hold tests. Remove this custom path only after those guarantees are verified. Long-term memory recording remains pending, not saved.
