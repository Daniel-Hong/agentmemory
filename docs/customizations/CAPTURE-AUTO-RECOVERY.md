# Verified capture quarantine reconciliation

Development only; operating .27, its storage-error hold and outstanding manual recovery remain unchanged. Default OFF. The existing authenticated capture dialog can persist ON/OFF through POST /agentmemory/capture/automatic-recovery with exactly {enabled: boolean}. A configured existing secret is required. No new credentials, external notifications or LLM calls. The environment opt-in remains available, but a persisted explicit setting takes precedence.

The existing retry scheduler reruns incomplete capture work within its own budget. This separate coordinator reconciles only quarantined transient failures whose original observation and current keyword/vector publication already exist. It never calls observe/compress/embedding, resets capture attempts, clears historical counts or recreates missing originals. Missing/conflicting/unknown content, active/manual retry, deletion markers and unready indexes stay blocked with a reason. Initial synthetic and compressed observation publications are supported; memory publications are rejected.

Every minute, at most one eligible item is considered after a 60-second cooldown, under existing manual/deployment/memory background admission. A durable checkpoint precedes completion changes. Six records (history, inbox, canonical original, intent, committed marker and receipt) are fully disk-certified against expected values, checked again under their record gates, then completion history/receipt and normal inbox removal are reconciled. Long full-file certification stays outside the gates. Unrelated record writes continue. A second complete certification and fresh-value check are required before resolved state is reported. A failed final proof leaves verification pending, not delivered success; subsequent work verifies without replaying capture. Three proof failures exhaust the item budget; repeated failures open a 30-minute circuit. No automatic reset of exhausted/blocked items.

Writer safety is limited to one compatible Linux worker, local engine and local file store on the same host. A parent-held flock FD excludes another participating worker. All StateKV mutations pass the selected-record gates; SDK write rejection latches automatic changes off because it does not cancel engine work. Redis, nonparticipating/direct writers, shared/network stores, copied/migrated lock metadata and forwarded engine connections are unsupported. Lock ownership is not proof of cancellation.

A retained v3 lock marker binds the canonical store path to host, boot, worker and native engine process identities. First installation records evidence but does not admit automatic mutations. A subsequent worker can enter after the old worker and old engine have actually ended and a different native engine owns the current SDK TCP connection. A PC reboot is not required for this verified cold boundary; a worker-only restart with the same dirty engine is insufficient. Verified clean admission may survive an ordinary compatible worker cycle. Elapsed time, a shutdown assertion and SDK disconnect alone are never proof of engine cancellation.

The evidence reader checks only the known engine PID, process start ticks/executable, worker/engine namespaces and the actual pinned SDK WebSocket socket tuple. The candidate must own both the unique matching listener and accepted server socket. Current ownership is rechecked before automatic changes. Foreign/copied/unsupported metadata is preserved and refused. An unobservable writer execution or surviving overlapping engine remains sticky-blocked; unknown boot identity cannot be cleared by a clean marker. Known uncertainty can only clear after a later proven OS boot where required. No stop, reboot, reset, privilege change or mark-safe endpoint is introduced.

ON is rejected under storage-error, manual/deployment hold, memory protection, circuit or uncertain writer admission. OFF closes local admission immediately, then persists and fully certifies the control record; the API distinguishes verified from unknown persistence. Concurrent ON/OFF and hold changes cannot revive a superseded enable request. Turning OFF does not erase pending verification, item budgets, historical counts or other holds. Control changes have content-free audit entries.

Existing status API exposes only aggregate enabled/supported/phase, resolved/verifying/blocked counts, whitelisted reason counts and circuit timing. HTML/Viewer keep unverified completion visible even when its normal inbox copy was removed. Private checkpoint identifiers/digests remain in the normal local state store and are never returned by this status. Historical 190 spool attempts have no individual identities and remain unknown history; this feature cannot retroactively prove their delivery.

Costs: up to three seconds of startup socket-evidence readiness polling, bounded process/socket metadata reads on admission, one small lock marker fsync at startup/verified shutdown; selected checkpoint writes and the existing full durable fences per eligible item. The SDK history/recovery list is still unpaged (hard accepted-row limits 5000/5001 do not bound transport allocation). No performance gain or hard SDK-memory bound is claimed. Unsupported or failed metadata reads halt the coordinator. No pruning of recovery evidence is implemented; reaching the cap requires inspection.

Validation uses synthetic fixtures, one Vitest fork and temporary HOME. No real engine, production originals, new LLM work, full browser suite or large benchmark runs in this phase. Full aggregate suite/release gate and representative live activation remain unverified due the user-requested low-load constraint after NVMe I/O errors. A code rollback must stop the newer worker before older code starts and retain checkpoint/lock/original/history state; older code will not interpret automatic recovery status. There is no data rollback.

Upstream replacement criteria: equivalent source/identity checks, atomic writer coordination, ACK-after-fsync proofs, interrupted verification resumption, explicit unknown outcomes, and the same conflict/deletion/hold tests. Remove this custom path only after those guarantees are verified. Long-term memory recording remains pending, not saved.


First-use operating scope still requires separate approval: install with recovery OFF; confirm native evidence is readable; use the existing supported lifecycle to terminate the worker and engine completely and start new processes; verify health, data preservation and independent holds; only then enable a limited pilot. This implementation performs none of those operating actions. The current storage-error hold must not be cleared as part of activation. All writers must participate; older/nonparticipating code invalidates the coordination assumption and requires a fresh verified engine boundary, not a worker-only restart.

The SDK 0.22.1 private WebSocket binding and Linux proc/socket parser have synthetic contract coverage, not live-host acceptance. Full aggregate, browser, installed-engine, cross-platform and load validation remain deferred under the low-load restriction. The historical OS-boot-only design at commit 0a7f7e1 is superseded by this verified native cold-start path.


Failure evidence follow-up: an unresolved checkpoint retains at most one whitelisted verification operation/stage/code and optional bounded elapsed time, so global trace eviction or coordinator restart does not erase its last failure category. Status exposes category counts only; no record identity, digest, trace token, raw error or original content. It reuses existing checkpoint writes with no new SDK read/write operations. Unknown causes remain UNKNOWN. This diagnostic correction cannot retroactively classify the three production failures and is not a performance fix.
