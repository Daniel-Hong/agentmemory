# Retained SDK sources versus capture capacity

The SDK backend intentionally retains capture originals because SDK completion is not disk or semantic completion. The admission cache incorrectly counted all retained rows against the 10,000 unprocessed-event cap, eventually blocking capture even with no active pending work.

Capacity now counts only rows without `storageCompletion: "sdk"`. Non-SDK dead, pending, retrying and unknown originals retain their existing cap protection. This is not an assertion that retained SDK records are verified, reconciled, indexed, or semantically complete. Proof pagination, unresolved review/history, SDK restore limits and source preservation remain unchanged.

SDK completion, reconciliation and deletion update an admission-only key Set under the existing admission lock. Key removal is idempotent. Status/sweep snapshots cannot overwrite this membership; SDK source restoration does not consume a pending slot. Normal completion does not invalidate the cache or rescan retained metadata. Unknown write results still invalidate conservatively. No data migration, record deletion, cap increase, retry relaxation or production change is involved.

Validation: new capacity regressions first reproduced two failures; 57 initial focused tests pass across capture capacity, SDK restore, durable capture, deleted capture and SDK preservation. Coverage includes warm/cold cache, actual pending saturation, unknown/dead originals, partial SDK proof/history preservation, repeated SDK delivery, disk cleanup and restoration while pending capacity is full. Evidence: workspace `capture-capacity-{red,green,final}.log`.

Upstream replacement criterion: upstream must preserve the same SDK originals/review evidence while distinguishing retained evidence from bounded unprocessed work and pass these acceptance tests. Additional key-Set tests cover one metadata scan across twelve SDK completions and stale status snapshots interleaved with pending admission/completion. Deployment is pending a separately approved release; this document is source verification only.

Final key-Set validation: 593 passed / 1 skipped in the broad parallel run, with one unrelated real-process SDK deadline case spooling under load. All 168 targeted tests (including that deadline suite) passed with one worker. Reconciliation membership has its own API regression; normal completed capture performs one initial metadata list, not one per event.

Lock-order regression: reconciliation finishes/releases its existing capture-key lock before acquiring admission for the single-row membership refresh. An initial wrapper held admission while waiting for capture-key (inverted order); the new regression first failed, then verifies admission stays available while reconciliation waits. No runtime/package deployment used the inverted wrapper.

Operating acceptance: `.71` was subsequently applied with normal clean shutdown and offline backups. Exact hashes of all 10,000 original rows matched after startup; a new observation was accepted and searchable, and SDK-v1 retry returned the same observation ID. The non-SDK pending/dead/unknown cap remains unchanged. Retained SDK archives have no newly introduced disk quota; existing memory/storage failure guards remain unchanged. Final affected suites (including the previously omitted SDK restore file) passed 86/86, and fixed lock-order plus loaded-final-code regression passed. See the integration note for full-run failures and bounded revalidation rather than interpreting the earlier broad run as all-green.
