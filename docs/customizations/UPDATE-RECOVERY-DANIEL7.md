# daniel.7 — 업데이트 진행 표시와 실패 복구

사용자 요구: 적용 버튼을 누른 뒤 요청이 접수됐는지·어느 단계인지 알 수 있어야 하며 실패 시 대응을 보완한다. 운영 .6 시도는 정상종료·최신 백업 후 사용자 설치가 실패했다. 기존 root 소유0755 releases 상위에 UID1000으로 mkdir하려던 조건을 합성 환경에서 재현했다. 새 버전 설치/activation 전이었고 사용자 수동 재시작 후 실제 .4 health=healthy/control=paused/mutationFailures=0을 확인했다. 최초 private 로그의 세부 오류는 관리자 인증 때문에 직접 읽지 못했다. 공개 job과 OS 권한/실패 재현이 근거다.

## 표시와 요청

클릭 즉시 요청 중 문구·UUID를 보이고 버튼을 비활성화한다. 긴 변경 설명 아래에서 눌러도 상태 영역을 보게 하며 sticky 상태·확인 단계 목록을 유지한다. 밝은 테마에서 잘못된 --text fallback(rgb238)이 흰 배경과 겹치던 문제를 --ink로 수정한다. 실패는 마지막 확인 단계·안전한 오류·이전 서버 복구 확인 여부로 표시한다. 복구 성공도 업데이트 성공으로 바꾸지 않는다.

네트워크 오류는 접수 결과 미확정이며 같은 ID를 조회한다. 새 요청의 확정4xx와 기존 미확정 요청을 재시도한4xx를 구분한다. 후자의 인증 거부는 기존 접수 부재 증명이 아니므로 ID를 보존한다. 서버는 화면에 나오는 최근10개뿐 아니라 전체 이력에서 같은 후보의 failed/interrupted를 확인해 새 실행을 거부한다. 과거 job/분석/제보와 실패 이력을 삭제하지 않는다.

## 운영 보호

신규 설치는 사용자 소유 `.local/share/agentmemory-personal-releases` 아래로 분리하고 기존 root 상위의 소유권·모드를 바꾸지 않는다. 운영 runtime/data 백업 안에 코드/node_modules 링크를 넣지 않는다. 실제 UID/GID1000 child의 쓰기/읽기 검사와 기존 의존성·baseline·archive guard를 서비스 중지 전에 완료해야 한다. 등록 시 --check-install-access로 실제 root→사용자 전환을 먼저 확인할 수 있다.

정상 종료가 인증되고 코드 미변경 또는 코드만 rollback 및 최신 데이터 보존/기존 guard가 확인된 경우에만 이전 서버를 한 번 재시작한다. 실제 이전 버전·저장 오류 없음·paused/active0를 재확인한 뒤 restored로 기록한다. 미인증 종료·데이터/guard 실패에서는 자동 재시작을 하지 않는다. 재시작·확인 실패는 restore_failed로 남기며 무한 재시도·강제 kill·오래된 데이터 복원·전역 queue replay를 하지 않는다.

root helper/unit/sudoers의 명령·권한은 확장하지 않는다. 공개 상세는 root 소유 kit 상태의 제한 필드만 읽고 작업 생성 시각 이전의 과거 상태는 합치지 않는다. 원문·환경값·로그·백업 경로는 공개하지 않는다. 운영 .4 및 발행 .6 bundle은 수정하지 않고 별도 .7 후보를 고정한다. .6이 성공 적용됐다고 가정하지 않는다. 동일 compatibility13은 기존 OS 클라이언트 경로를 유지한다.
