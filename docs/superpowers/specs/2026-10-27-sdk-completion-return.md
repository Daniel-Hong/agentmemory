# SDK completion return

Approved direction: return ordinary work to the official SDK completion boundary. No operating rollout. Start at d8d555a; rejected deadline priority changes are excluded. Use an isolated feature branch instead of changing personal/upstream history.

Use a separate SDK completion result path in the existing mutation/capture tracker as StateKV's default for file-backed ordinary work. Keep mutation freeze/drain, sticky SDK failure, original per-request deadlines and pinned SDK value comparisons; never read/parse/fsync whole state namespace files for SDK completion. Results explicitly say completed=true, completion=sdk, synced=false. Keep the strict disk fence implementation for explicitly selected proof work/tests, not as an automatic fallback.

Background pause/drain and normal shutdown accept honest SDK completion with no uncertain mutation. Shutdown distinguishes completed from verified (disk proof); CLI understands that distinction, and writer-clean admission is never inferred from SDK completion alone. Health/UI show the reduced guarantee. Existing holds, error history and recovery budgets are never reset.

Capture receipts never return durable=true for SDK-only results. Existing collector removal predicates remain unchanged and installed hooks are not updated. Auto quarantine reconciliation cannot make a durable-completion claim in SDK mode and must be blocked before spending proof budget. Manual replay/destructive cleanup remains gated by disk proof or explicit unavailability. Inspect all original-removal boundaries before allowing a new SDK result to reach them; pending originals must not disappear merely because a new completion enum exists.

Rejected alternatives: returning synced=true would lie; globally removing guards/nulling the fence would break background control and embedding contracts; changing collector durable predicates would expand the approved source-removal boundary. Remaining queue/quarantine items may remain pending while ordinary background work can complete; report this limitation rather than silently weakening receipt requirements.

Validation: test failures first at default StateKV completion, missing namespace/no physical proof, sticky SDK error and explicit shutdown completed-but-not-verified. Add cancellation/deadline/expected-value/drain, receipt false/auto budget-retention and source-removal boundaries. Use small synthetic/mocked SDK and real tiny temporary files only where required. One fork and isolated HOME; no engine/socket/load/real provider or operating mutations. Build/docs and independent review before candidate preparation. No push/deployment/restart/resume.

Implementation clarification: reuse the existing freeze/drain/revision/SDK-capture machinery with an explicit sdk mode rather than duplicating an independent tracker. Direct factory default remains disk for explicit proof tests; StateKV selects sdk. SDK-stored inbox originals carry a tag, are excluded from replay/prune/active-stall counts and remain queued for ownership proof. Existing manual retry jobs and automatic quarantine recovery fail closed before mutation in sdk mode. Managed spool settlement/drain is held and capture API omits boot/time-based durability promises. No installed client changes.

## Final capture compatibility boundary

The initially conservative global SDK 503 draft was rejected as a normalization candidate. Fresh senders now opt in with sdk-v1, preserve their originals separately before release from retry state, and receive SDK-only acknowledgement after actual completion. Historical/receipt-required records never acquire the policy implicitly. Updated clients park permanent SDK-only holds without a retry-count increase or head-of-line block. Shared SDK originals and compatibility accepted-originals are bounded; full storage prevents new admission, with no original eviction. Client installation remains a separately disclosed operating step. See SDK-COMPLETION-RETURN.md for exact mixed-version and quota behavior.
